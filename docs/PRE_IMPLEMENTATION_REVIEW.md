## 1. 結論

機能仕様は十分に具体化されている。一方、組版エンジンの能力、Markdownの局所書き戻し、PDFとプレビューの同一性が成立するかは未検証。アプリ全体を組み始める前に、詳細設計の最小契約と独立したPoCで確認する。PoCは製品実装と区別し、暫定API・保存形式を製品に固定しない。

優先度: P0 = アーキテクチャ・原稿保全・出版の成立条件、P1 = 詳細設計で解決、P2 = 実装・配布・品質評価。P0は全て同じ種類の作業ではない。利用者判断、詳細設計、実測、法的確認を区別する。

## 3. 現行文書の記述上の不整合・補足

以下は仕様変更と区別して修正候補として管理する。

- §2の「章は原稿ファイル等で定義」とF05-4の「章はH1、ファイル境界と独立」を区別する。管理上のセクションと意味上の章を別用語にする（R13）。
- §2のLayoutの正本欄にはMarkdownから参照されるCanvas宣言ファイルも含める（Q04で合意済み）。
- F03-2の「次の完全な見開き」とF05-3の欠けた面の扱いを区別する。start/end条件は内頁面を指定するだけ、固定見開きだけは実際に二面を確保する。表紙を含む出力での面整合はQ10。
- F03-2のoverflowPolicyがsplitPolicy=strictを暗黙に緩和しないよう制約を統合する。
- F09-1の数式記法の例でインラインとブロックが同じドル記号1個になっている。ブロックはドル記号2個の候補とする。正式文法は別途確定。
- F05-3におけるPDF面と内頁面の区別は正しいが、PDF通し位置は出力プロファイルごとに変わる派生情報とする。計画内IDは同一計画内だけの識別子。
- F05-1の状態とF03-3の未適用テーマ案は別の状態軸にする。未適用案で確定版を置換しない。
- §7.1の採用技術方針と第一検証候補を区別する。組版エンジン、パッケージマネージャ、具体的な依存バージョンは未確定。

## 4. 利用者回答と残る判断（2026-11-26）

### Q09 正式出版確認 — 回答済み
HTMLプレビューを使用し、出力実行時にPDFを生成する。初回レビューの「PDFそのものを出版前に表示する」推奨案は採用しない。PagePlanと描画条件を固定し、正式PDFの紙面を検査する。独立した再改ページを避ける設計、照合方法・許容差はPOC-04で確認する。

### Q10 表紙込みPDFと両面印刷 — 回答済み
電子閲覧用と両面印刷用を分離する。電子閲覧用では面整合だけの実空白を原則追加しない。両面印刷用では必要な面調整空白を表示して出力する。内頁面と印刷番号は維持する。具体的な開始面・印刷条件は詳細設計・PoCで検証する。

### Q11 将来のWeb版のPDF出力 — 保留
ローカル生成を優先するという希望を記録。ブラウザ内生成を検証するが、正式Web出力の方法やサーバー提供は未決。原稿の無断送信は行わない。

### Q12 continuousと部品側の自動改ページ — 方針回答済み、適用範囲確認待ち
continuousでは部品側の自動改ページ設定も無効にする。初回レビューの「部品設定をそのまま有効にする」案は採用しない。境界の先頭ブロックのstartPositionだけを抑制する案と、当該セクション全体の部品由来自動開始条件を抑制する案のどちらかは未確定。手動改ページ、固定ページ/見開き、番号区間、物理的なページ不足の処理は維持する案。原稿・テーマを自動変更しない。

### Q13 初期公開 — 回答済み
基本機能が通しで動く段階で開発版を公開する。既存の全製品要件を削減するものではない。安全性、原稿保全、形式互換性の説明、依存ライセンス確認を公開前に行う。

### Q14 ライセンス — 保留
MITで公開したいという希望を技術選定の優先条件として記録する。以前のApache 2.0候補を置き換える。依存ライブラリと実装形態の確認後に最終決定し、現時点ではLICENSEを追加しない。

### 追加方針 — 独自実装
必要な機能が既存技術で実現できない場合は自前で実装する。既存エンジンに合わせて合意済み要件を縮小しない。独自TypeScript組版エンジンを有力候補として、HTML/CSS/SVGによる描画・文字計測、ページ割付・制約・断片対応、固定ページ描画からのPDF生成を試す。汎用描画・文字処理・PDF等まで全て再実装することは前提としない。既存候補との比較、MITとの依存整合、性能・保守負担を検証し、最終採用を決める。

5. 利用者判断と主要PoCの合格を確認してから、Coreの製品実装に進む。
